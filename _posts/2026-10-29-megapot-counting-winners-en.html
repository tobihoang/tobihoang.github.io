A million tickets, none re-checked: how does Megapot count winners on-chain?

Megapot is a lottery run by smart contracts on the Base network: you buy tickets in USDC, there is one draw a day, and prizes are paid straight from the contract. This is a technical analysis, not advice to play the lottery or to invest.

Megapot sells thousands of tickets every day, yet when it settles a draw the contract never opens a single ticket to compare it. So how does it know who won, in which tier, and how much each person gets, without ever running out of gas? And why doesn't your prize shrink when lots of other people win too?

This post follows one ticket through the contract: buy, store, draw, settle, pay, claim. Each part starts with a question, tries the naive approach first, looks at where it breaks, and only then shows how Megapot solves it.

If you play Megapot and only want to know how prizes are worked out, read Question 7 and the part about duplicate tickets at the end of Question 4. If you write smart contracts, the most useful parts are Questions 4 to 6, the lab and the summary table at the end.

Based on the source code from the Code4rena audit (11/2025). The contract running on Base may differ from this version.

Summary
  • A ticket is a single uint256: bit n set means number n was picked. Comparing two tickets takes one AND.
  • On purchase, the contract updates a count table stored on-chain: each cell records how many tickets contain a particular group of numbers, and each ticket bumps 31 cells.
  • On settlement, it reads only the 31 subsets of the winning numbers, then uses inclusion–exclusion to get the exact number of tickets in each tier.
  • Prize money is split across every combination that could win, including ones nobody bought. That is why your prize doesn't drop when many others win the same tier.

The life of a ticket

This is the full life cycle of a draw inside the contract. The questions below walk through each step in turn.

Question 1: what makes settling a draw hard?

When Pyth Entropy delivers the random number, it calls the Jackpot's scaledEntropyCallback. Within that one transaction, the contract has to know how many winning tickets each tier has, so it can work out each tier's payout.

The naive approach everyone thinks of first: store the list of tickets, and at settlement loop over every ticket and compare it with the result.

naive approach, not Megapot's code 
for (uint256 t = 0; t < tickets.length; t++) {       // 10,000 tickets = 10,000 iterations
    uint8 hits = countHits(tickets[t].normals, winning);  // read the ticket from storage, compare
    bool b = tickets[t].bonus == winningBonus;
    tierCount[2 * hits + (b ? 1 : 0)]++;
}

Where does it break? Every transaction has a gas limit. Pyth's callback is even tighter: it runs with a gas budget the contract sets in advance, entropyBaseGasLimit + 250,000 × bonusballMax, a few million gas with 10 bonus balls. Reading one untouched storage slot alone costs about 2,100 gas, so 10,000 tickets is over 21 million gas, far beyond that budget. The more tickets sold, the longer the loop, until one day the settlement transaction runs out of gas halfway through. The draw gets stuck and nobody gets paid.

Megapot solves this by moving the cost: the heavy work is done up front at purchase time, and each buyer pays the gas for their share in their own transaction. By settlement, only a fixed amount of work is left. That takes three pieces: bitmap tickets, a count table keyed by number groups, and inclusion–exclusion.

Question 2: how do you store a ticket?

The naive approach is to store exactly what the buyer sends: an array uint8[] [3, 9, 11, 13, 28] plus a bonus number. To find how many numbers two tickets share you compare every pair, 5 × 5 = 25 comparisons, and blocking duplicate numbers in a ticket also needs nested loops.

Megapot does it differently: it packs the whole ticket into one uint256, treating each bit as a checkbox:

  • bit 0: unused (there is no number 0)
  • bits 1 to 30: normal numbers, bit n set means number n was picked
  • bits 31 to 40: bonus, bonus b sits at bit 30 + b

Bit n is worth 2ⁿ. When printed in binary, the low bits are on the right like the ones digit in a decimal number, so you read a binary string from right to left. Change the ticket below to see it:

Packing a ticket: OR, bit by bit

The buyer sends a plain array of numbers (struct Ticket { uint8[] normals; uint8 bonusball; }). The contract converts it to a bitmap with a short loop:

contracts/lib/TicketComboTracker.sol · toNormalsBitVector 
uint256 bitVector = 0;
for (uint256 i; i < _set.length; ++i) {
    require(_set[i] <= _maxNormalBall && _set[i] > 0, "Invalid set selection");
    require((bitVector & (1 << _set[i])) == 0, "Duplicate number in set");
    bitVector |= 1 << _set[i];
}
// then in insert(): put the bonus above the normal numbers
ticketNumbers = set | 1 << (_bonusball + 30);

The two bit operations do opposite jobs. OR | merges: it adds bits, and a bit that is already set stays set. AND & filters: it keeps only the bits both sides have. The second require uses AND to check for duplicates: if bit n is already set, the result is non-zero and the transaction reverts.

When bits don't overlap, OR gives the same result as addition (2² | 2⁴ | 2⁵ = 4 + 16 + 32 = 52). But if a number is entered twice, addition carries into another bit and produces the wrong ticket (4 + 4 = 8, which is number 3). OR doesn't have that problem, and the contract blocks duplicates before that anyway.

Question 3: how do you tell how many numbers a ticket matched?

The naive approach with arrays is two nested loops:

naive approach 
for (i = 0; i < 5; i++)
    for (j = 0; j < 5; j++)
        if (ticket[i] == winning[j]) hits++;     // 25 comparisons

With a bitmap, the contract does it in exactly two operations. AND keeps the numbers that both the ticket and the result have, then popCount (from the Solady library, fixed gas cost) counts the 1 bits:

contracts/Jackpot.sol · _calculateTicketTierId 
uint256 matchingBits = _ticketNumbers & _winningNumbers;
matches = LibBit.popCount(matchingBits);
uint256 ticketBonusball  = _ticketNumbers  >> (_normalBallMax + 1);   // >> 31: drop the normal numbers
uint256 winningBonusball = _winningNumbers >> (_normalBallMax + 1);
uint256 bonusballMatch = (ticketBonusball == winningBonusball) ? 1 : 0;
return 2 * (matches - bonusballMatch) + bonusballMatch;

The contract has no if (bit > 30) anywhere to recognise the bonus. A bit's meaning comes from its position: normal numbers never go above bit 30, so shifting right by 31 bits leaves only the bonus. To turn the bonus back into a number, unpackTicket takes the position of the highest set bit (LibBit.fls) and subtracts 30.

The last line is a trick for flattening a 2-D table into a 1-D array. A tier has two pieces of information, k numbers matched (0 to 5) and bonus or not, so the tiers are laid out in 12 slots with index = 2k + bonus:

Question 4: how do you count each tier's tickets without looping over tickets?

Comparing one ticket is already cheap. But settlement still needs the total number of tickets in each tier, and Question 1 showed we can't loop over tickets.

Second try, still naive: at purchase time, count by whole ticket, something like count[ticket] += 1. The jackpot tier is easy: read exactly one cell, count[result]. But what about "3 numbers + bonus"? You'd have to list every possible ticket with exactly 3 matching numbers and read each cell, that is 10 × C(25,2) = 3,000 cells. Add up every tier with at least one matching number, across all 10 bonus columns, and you get 893,760 reads. No more loop over tickets, but still far too heavy.

Megapot's idea (the TicketComboTracker library): don't count by whole ticket, count by every subset of the ticket. Each time a ticket is sold, bump the counter for every group of numbers inside that ticket. Then the question "how many tickets contain both 3 and 11?" is just one cell read.

In this post I call these counters the count table. It is a table in the contract's storage (the comboCounts mapping). Each cell belongs to one group of numbers, say {3, 11}, and holds a single number: how many tickets sold so far contain that group.

A 5-number ticket has 2⁵ − 1 = 31 non-empty subsets. Each subset is also a bitmap, which is just a number, so it can be used directly as the mapping key. These are the 31 cells the ticket above will bump (change the ticket above and this list follows):

contracts/lib/TicketComboTracker.sol 
struct ComboCount { uint128 count; uint128 dupCount; }     // fits in 1 storage slot
struct Tracker {
    uint8 normalMax;       // 30
    uint8 bonusballMax;    // changes per draw, e.g. 10
    uint8 normalTiers;     // 5
    mapping(uint8 => mapping(uint256 => ComboCount)) comboCounts;  // [bonus][subset bitmap]
    mapping(uint8 => ComboCount) bonusballTicketCounts;            // [bonus] total tickets
}

// insert(): runs for each ticket at purchase
isDup = comboCounts[_bonusball][set].count > 0;              // has someone already bought all 5 + bonus?
for (uint8 i = 1; i <= 5; i++) {
    uint256[] memory subsets = Combinations.generateSubsets(set, i);   // C(5, i) subsets
    for (uint256 j = 0; j < subsets.length; j++)
        isDup ? comboCounts[_bonusball][subsets[j]].dupCount++
              : comboCounts[_bonusball][subsets[j]].count++;
}

Three details worth noticing:

  • The table doesn't record who bought which ticket, only counts. Ownership lives in the ticket NFT, somewhere else.
  • The bonus is the outer key, not a bit inside the subset. A bonus either matches or it doesn't, there is no "partial match", so it gets its own column. Putting the bonus bit into the subset would make each ticket write 2⁶ − 1 = 63 cells instead of 31.
  • The table has a finite size. Each bonus column has at most C(30,1) + C(30,2) + … + C(30,5) = 174,436 cells. Selling more tickets only makes the counts in those cells go up.

Each draw has its own count table: mapping(uint256 => TicketComboTracker.Tracker) drawingEntries. The draw result isn't in the count table; it lives in drawingState[draw].winningTicket.

Side question: has anyone already bought this ticket?

The cell for the full 5-number subset is exactly "the number of tickets identical to this one". So checking for duplicates is one cell read: comboCounts[bonus][set].count > 0. The contract also exposes a view function, checkIfTicketsBought(drawingId, tickets), so an app can ask before buying, for free since it is a view. This is worth knowing because duplicate tickets have to share the jackpot (Question 7).

Question 5: how do you list 31 subsets in Solidity?

The naive approach is hard-coded nested loops: 2 loops for 2-number subsets, 3 loops for 3-number subsets, and so on. Long code, one block per size. Recursion, on the other hand, costs gas on every call and can hit the EVM's stack depth limit.

Megapot uses one general function, generateSubsets(set, k), for every k, with no recursion, by splitting the work into two layers.

  1. Pick positions with a small 5-bit number called comb. Bit j set means "take the j-th number of the ticket". The ways to pick exactly k numbers are exactly the 5-bit numbers with exactly k 1-bits.
  2. Translate positions into real numbers: walk through the ticket's bits, and each time you hit one of the ticket's numbers, read one bit of comb to decide whether to keep it.

The starting point is (1 << k) − 1, k 1-bits at the bottom (the smallest number with k 1-bits). The stopping point is 1 << 5 = 32, because going past 5 bits means picking a "6th number" the ticket doesn't have. The step is Gosper's hack: three bit operations that jump straight to the next larger number with the same count of 1-bits, skipping every invalid number in between.

contracts/lib/Combinations.sol · generateSubsets 
uint256 bound = 1 << n;             // n = popCount(set) = 5 → 32
uint256 comb = (1 << k) - 1;        // k = 2 → 0b00011
while (comb < bound) {
    // layer 2: comb (positions) → mapped (bitmap of real numbers)
    for (uint256 i; i < 256 && _set != 0; ++i) {
        if (_set & 1 == 1) {                      // bit i is one of the ticket's numbers
            if (_comb & 1 == 1) mapped |= (1 << i);
            _comb >>= 1;                           // move to the next position
        }
        _set >>= 1;
    }
    subsets[count++] = mapped;
    // layer 1: Gosper's hack
    uint256 c = comb & uint256(-int256(comb));   // lowest 1 bit
    uint256 r = comb + c;                        // push the lowest block of 1s up
    comb = (((r ^ comb) >> 2) / c) | r;          // put the leftover 1s back at the bottom
}

One thing worth noting: comb is never stored anywhere. It's just a temporary counter. The subsets array also lives in memory and disappears when the transaction ends. The only things written on-chain are the comboCounts[bonus][mapped] cells.

Question 6: after reading the count table, why are the numbers wrong?

Once the result is in, the contract takes the 31 subsets of the winning numbers and reads the matching cells in the count table across every bonus column. The column for the winning bonus is added to the "with bonus" tiers, the other columns to the "without bonus" tiers. With 10 bonus balls that's 31 × 10 = 310 reads.

But the totals it reads are double counted. A ticket that matched 3 numbers, say {3, 11, 15}, contains 3 pairs from the result: {3,11}, {3,15}, {11,15}. So when you add up by pair, that ticket is counted 3 times in the "2 numbers" row. In general: a ticket that matched m numbers is counted C(m, k) times in row k.

The fix is to work from the top down. The 5-number row has nothing mixed in, so it reads straight. The 4-number row subtracts the 5-number tickets that were counted in it. The 3-number row subtracts the 4- and 5-number tickets, and so on:

contracts/lib/TicketComboTracker.sol · _applyInclusionExclusionPrinciple 
for (uint256 k = 5; k >= 1; --k) {                // from the 5-number tier down
    uint256 s  = _matches[2*k];                   // total read from the table, no bonus
    uint256 sp = _matches[2*k+1];                 // with bonus
    for (uint256 m = k + 1; m <= 5; ++m) {
        uint256 c = Combinations.choose(m, k);    // a ticket matching m numbers contains C(m,k) k-groups
        s  -= c * result[2*m];                    // result[2m] was computed in an earlier pass
        sp -= c * result[2*m+1];
    }
    result[2*k] = s;  result[2*k+1] = sp;         // filled in now so lower rows can use it
}

The "bonus only" tier has no 0-number subset, so it is computed separately: take the total tickets with the right bonus (bonusballTicketCounts) and subtract the bonus tickets that also matched normal numbers.

Question 7: how do you split the money without knowing who won?

Now that we know how many tickets are in each tier, we need to know how much each ticket gets and who to pay.

The naive approach is the traditional even split: take the tier's share of the money, divide by the number of actual winners, then loop over the winners and transfer. This has three problems:

  • It needs a list of winners and a transfer loop again, exactly what Question 1 ruled out.
  • A single recipient that refuses the payment (for example a contract that deliberately reverts) breaks the whole settlement transaction.
  • Each person's prize depends on how many others won, so nobody knows in advance what a prize is worth.

Megapot differs in two ways. First, settlement only computes and stores each tier's payout, and players come to claim later (Question 3), so there is no transfer loop. Second, and more interesting, is the denominator: GuaranteedMinimumPayoutCalculator does not divide by the number of people who actually won. It divides by the total number of combinations that could win that tier, whether anyone bought them or not, plus the number of duplicate tickets:

contracts/GuaranteedMinimumPayoutCalculator.sol 
tierWinners[i] = _calculateTierTotalWinningCombos(k, 30, bonusballMax, coBonus) + _dupResult[i];
// with bonus:    C(5,k) × C(25, 5−k)
// without bonus: C(5,k) × C(25, 5−k) × (bonusballMax − 1)

premium    = remainingPool × weight[i] / tierWinners[i];
tierPayout = (minPayoutTiers[i] ? minPayout : 0) + premium;
totalPayout += tierPayout × (uniqueResult[i] + dupResult[i]);   // only paid for tickets actually sold

The share belonging to combinations nobody bought isn't paid to anyone; it stays in the LP pool. That one denominator has two important consequences for players:

  • Your prize doesn't shrink when many others win the same tier. Whether 1 or 500 people hit "3 numbers + bonus", each gets the same amount.
  • It is only split when someone buys exactly your ticket (dupCount). In practice that only matters for the jackpot. So picking particular numbers doesn't make the small tiers worth more.
An example with assumed parameters. The minimum payout and each tier's weight are set by the owner and are not in the code. Assume a $1,000,000 pool, a $1 minimum for every paying tier, and weights estimated from earlier API data (3 numbers + bonus 4%, jackpot 33%), not checked on-chain. The minimums take 377,640 combinations × $1, leaving $622,360. Each "3 numbers + bonus" ticket gets about $1 + 622,360 × 4% / 3,000 ≈ $9.30. The jackpot gets about $1 + 622,360 × 33% ≈ $205,381, and if 2 people bought the same jackpot ticket, each gets about half.

Note that at settlement the contract only computes and stores tierPayouts[draw][tier]. It doesn't send anyone money yet. Players claim their ticket NFT later; only then does the contract compare that one ticket with AND + popCount as shown earlier, pay out, and burn the NFT so it can't be claimed twice.

Question 8: what's the cost?

Nothing is free. This design moves the cost elsewhere, and it has a few weak spots worth knowing:

  • Buying costs more gas. Each ticket costs about 31 storage writes, plus minting the NFT. Writing a brand-new slot costs about 20 thousand gas, an existing one about 5 thousand. It's still cheap on Base, but buying many tickets in one transaction adds up.
  • Settlement cost grows with the number of bonus columns. The number of reads is 31 × bonusballMax, and bonusballMax goes up as the pool grows. This is the root of audit finding H-02: if bonusballMax gets too high, the callback runs out of gas and the draw gets stuck, exactly the failure the design is meant to avoid.
  • A little waste in the code. At settlement, generateSubsets is called again inside the bonus loop, so the 31 subsets are recomputed 10 times. That is only memory computation, much cheaper than storage reads, but it could be moved out of the loop.

Recap: the problem, the naive way, Megapot's way

What to take away

Lottery aside, these are design patterns that apply to other contracts:

Do the work on write so reads have a ceilingIf some step has to run in a single transaction (settlement, liquidation, distribution), move the size-dependent cost into users' own small transactions. The mandatory step is left with a fixed cost.
Bitmaps as sets and as keysOne uint256 holds a set of up to 256 elements. Intersection, union and membership are each one bit operation, and each set is exactly one number, so it works directly as a mapping key.
Count instead of storing identitiesThe table holds only counts, not who bought what. Identity lives elsewhere (the NFT) and is only touched when its owner comes to claim.
Pull payments, don't push themSettlement only computes each tier's payout. Players claim for themselves, so there is never a loop sending money to thousands of wallets.
A denominator that doesn't depend on playersSplitting across every possible combination keeps each tier's value stable and hard to manipulate: nobody can dilute other people's prizes by piling into one tier.
