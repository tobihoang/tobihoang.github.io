Part 2 · on-chain randomness

How does Megapot draw its numbers, and can you trust it?

Megapot is a lottery run by smart contracts on the Base network: you buy tickets in USDC, there is one draw a day, and prizes are paid straight from the contract. This is a technical analysis, not advice to play the lottery or to invest.

Megapot has no draw machine. Every day after 17:00 UTC, the contract asks a service called Pyth Entropy for a random number, then turns that number into 5 numbers and 1 bonus by itself. This post explains how that works, how transparent and how safe it is, and then checks a real draw from scratch.

This is part 2. Part 1 covers how the contract stores tickets and counts winners. I read Pyth's source code and Megapot's Code4rena audit (11/2025), pulled the data from Basescan, and recomputed every number in this post myself.

TransparencyHigh

Every step is on-chain and anyone can recompute it. I checked draw 133 (4 Aug 2026) and everything matched.

Safe from playersHigh

Players, whoever triggers the draw and Base's sequencer can't predict or change the result, as long as Pyth is honest.

Still need trustTwo parties

Pyth, which knows the result a few seconds before everyone else and could refuse to answer. Megapot's owner, who can replace the random number source entirely.

Why does Megapot need an outside service?

A smart contract can't produce a safe random number on its own. The only things a contract can read that look random are block data, like the time (block.timestamp) or block.prevrandao. But whoever builds the block knows these values before anyone else. On Base, that's the sequencer run by Coinbase. If Megapot took its winning numbers from block data, the sequencer would know the result in advance. So Megapot uses an outside service: Pyth Entropy.

What is Pyth Entropy?

Pyth Network is an oracle network, meaning a service that brings outside data onto a blockchain. Pyth is best known for asset price feeds used by DeFi apps. Pyth Entropy is a separate Pyth product that supplies random numbers to smart contracts on many EVM chains, including Base. The best-known service of the same kind is Chainlink VRF.

Using it is simple: an app that needs a random number (a game, an NFT mint, a lottery) calls the Entropy contract and pays a small fee in ETH. A few seconds later, Entropy calls the app back (a callback) with the random number. Entropy has two roles:

  • Provider: the party that holds the secret and sends it when asked. On Base, the default provider is run by Pyth itself, using software called Fortuna.
  • Requester: here, Megapot's contract.

The Entropy contract on Base lives at 0x6E7D…81Bb, and every request and every answer can be looked up on the Pyth Entropy Explorer.

How it works: two secret halves, mixed into one

Under the hood, Pyth Entropy uses commit, then reveal (commit–reveal). Whoever holds a secret must first publish its fingerprint (its hash). When the number is needed, they publish the number itself, and anyone can hash it again to check that it's the number they committed to. A Megapot draw goes through four steps:

  1. Step 1
    Ticket sales close (17:00 UTC). Anyone can call runJackpot(). The draw is locked: from here on nobody can buy more tickets.
  2. Step 2
    Megapot sends a request with a fee to Pyth Entropy. Entropy creates the first half from block data and records it publicly on-chain.
  3. Step 3
    A few seconds later, Pyth sends the second half, the secret number Pyth committed to earlier. The contract checks this half against the commitment, then hashes the two halves into one 256-bit random number.
  4. Step 4
    In that same transaction, Megapot turns the 256-bit number into 5 numbers and a bonus, counts the winners, splits the prizes and opens the next draw.

The idea: when Megapot sends its request, nobody except Pyth knows the second half. When Pyth committed, Pyth didn't know the first half. Neither side can pick the result alone.

Why can't Pyth change its half?

Pyth doesn't commit separately for each request, because that would be too expensive. Instead, Pyth picks one secret starting number and hashes it over and over, millions of times, building a hash chain. Pyth publishes only the last link of the chain. Each request after that uses the next link going backwards, and anyone can check it: hashing the new link must give exactly the link that was published before it.

The keccak256 hash can't be reversed, so knowing an old link doesn't help you guess the next one. And because the old link is already on-chain, Pyth can't hand over a different number that still matches.

What's in Megapot's first half?

In the original design, the requester keeps a secret number of its own. Megapot doesn't send one, so Entropy builds the first half itself with this function:

Entropy.sol (Pyth) 
_state.seed = keccak256(abi.encodePacked(
    block.timestamp,     // chosen by the sequencer
    block.prevrandao,    // already public from the Ethereum block
    msg.sender,          // Megapot's contract, fixed
    _state.seed          // changes after every request from any app on Base
));

This half isn't secret: anyone running a node can compute it as soon as the transaction lands in a block, and the sequencer knows it even earlier. So all of the secrecy sits with Pyth. The promise that "only one side needs to be honest" becomes "Pyth must be honest". Pyth's documentation states this condition clearly for requesters that don't supply their own secret.

From one 256-bit number to six balls

Megapot lines up the numbers 1 to 30 and shuffles them with the Fisher–Yates algorithm: walk from the end of the line to the start, swap each position with a random position in front of it, then take the first 5 numbers. Each step gets a small random number by hashing the 256-bit number together with a counter. The contract throws away values that would make the remainder biased (rejection sampling), so every number is equally likely. The bonus, 1 to 10, works the same way.

How transparent is it? I checked draw 133 myself

"Transparent" here means: you don't need to take Megapot's or Pyth's word for anything. Public data and a keccak256 function are enough to recompute the result. I picked draw 133 because Megapot itself posted this draw's transaction in a post about one of its winners. That draw came out 10, 14, 25, 26, 27 with bonus 4.

  1. 16:54:51
    Pyth answers another app and reveals the link 0x2c2d…c1ca. View transaction
  2. 17:00:17
    Megapot requests a number (request 556741). The first half is 0x223b…d8d5. View transaction
  3. 17:00:21
    Pyth sends the second half 0xe1fd…b645. The same transaction produces the random number 0x4f36…ee8e and the six balls. View transaction

From these three transactions, I could check five things:

  1. ✓
    Pyth didn't swap its number. Hashing the second half 0xe1fd…b645 gives exactly 0x2c2d…c1ca, the link Pyth revealed 5 minutes earlier.
  2. ✓
    The commitment matches. The two halves match the commitment Entropy recorded when Megapot made its request.
  3. ✓
    The random number is right. keccak256 of the two halves gives exactly 0x4f36…ee8e.
  4. ✓
    The six balls are right. A Fisher–Yates shuffle from that number gives exactly 25, 27, 14, 26, 10 and bonus 4, in that order.
  5. ✓
    The prize total is right. Winning tickets in each tier times each tier's payout adds up to exactly the 1,743.95 USDC the contract recorded as paid to players.

A side finding: the live contract differs from the audited one

On my first try, I used the code from the audit exactly: the 5 normal numbers and the bonus share one seed. That gave 9, 15, 7, 12, 28 and bonus 1, completely wrong. Trying again with a separate seed for each set (hashing the random number with the set's index) gave the right answer. The odds of matching by luck are about 1 in 171 million.

Audited version, shared seed: 915712281 Live version, one seed per set (matches on-chain): 25271426104

That's good news. Code4rena had reported issue M-05: a shared seed means the normal numbers and the bonus aren't independent. Simulating the audited version shows the bonus equals one of the normal numbers in about 18.4% of draws, instead of 16.7%. Draw 133 shows Megapot has fixed this. That conclusion rests on one draw; you can check more draws yourself with the tool below.

This one transaction runs a whole chain of nested calls. Who sends the transaction doesn't matter: the contract only accepts it if the two halves match the commitment.

call tree of the reveal transaction 
Fortuna (Pyth's wallet)
└─ Entropy.revealWithCallback(...)          check commitment, compute randomNumber
   └─ ScaledEntropyProvider._entropyCallback turn 32 bytes into 6 balls
      └─ Jackpot.scaledEntropyCallback       count winners, split prizes, open draw 134
         └─ PayoutCalculator                 compute each tier's payout

If the call into Megapot fails (say, it runs out of gas), Entropy doesn't revert the whole transaction; it records a "callback failed" status. After that, anyone can call it again with the same two halves, so the result doesn't change.

A Python script to run it yourself

Requires pip install pycryptodome.

verify_draw_133.py 
from Crypto.Hash import keccak
def k(b):
    h = keccak.new(digest_bits=256); h.update(b); return h.digest()

user = bytes.fromhex("223b90698bc57d34e84f55c059f3bb7a4054dcd82220ae661bdebd1d60fdd8d5")
prov = bytes.fromhex("e1fdeec9d5d8f924f96fcd3c3fbf06cd85e762d0013746d0a6153c9720f0b645")

print(k(prov).hex())                    # 2c2d6b1e…c1ca  = link 556740
print(k(k(user) + k(prov)).hex())       # 91bf6648…c7a3  = commitment
rnd = k(user + prov + bytes(32))
print(rnd.hex())                        # 4f367621…ee8e  = randomNumber

MAX = 2**256 - 1
def draw(lo, hi, count, seed):
    pool, nonce = list(range(lo, hi + 1)), 0
    for i in range(len(pool) - 1, 0, -1):
        while True:
            r = int.from_bytes(k(seed + nonce.to_bytes(32, "big")), "big"); nonce += 1
            if r < (MAX // (i + 1)) * (i + 1): break
        j = r % (i + 1); pool[i], pool[j] = pool[j], pool[i]
    return pool[:count]

seed = lambda i: k(rnd + i.to_bytes(32, "big"))   # keccak256(abi.encode(randomNumber, i))
print(draw(1, 30, 5, seed(0)), draw(1, 10, 1, seed(1)))   # [25, 27, 14, 26, 10] [4]

How safe is it? Who could cheat?

In a normal draw, nobody can choose the result. But the parties aren't equal in what they know or what they're allowed to do. The table below is based on the Pyth code that's live and the audited Megapot code:

PartyKnows what, and whenCanCan't
PlayersThe result at 17:00:21, like everyone elseNothing that mattersBuy tickets after the draw locks at 17:00:17
Whoever calls runJackpotThe user half, once the transaction is in a blockPick when to call, which changes the user halfPredict the result: without Pyth's half, changing the timing doesn't help
Base sequencerThe user half, before anyone elsePick the timestamp, ordering and block for the request transactionSame as above, unless it colludes with Pyth
Pyth (provider)The result at 17:00:17, 4 seconds before everyone elseRefuse to answer, leaving the draw stuckChange its half: the hash chain is locked
Megapot ownerSame as playersReplace the random number contract, change the provider, unlock a draw in progressChange the result of a draw that's already been answered

The specific risks, from most to least serious

1. Megapot's owner replaces the random number sourceIn the audited code, setEntropy lets the owner swap out the whole random number contract. The lottery contract only checks "did this number come from the configured contract?", so a replacement contract could send back any six numbers it likes. setEntropyProvider changes the provider, and in the audited code it doesn't emit an event. Code4rena filed changing the provider mid-draw under issues M-06 and M-07. This is the biggest point of trust, and it's about operations, not the algorithm.
2. Pyth knows first and could refuse to answerAs soon as Megapot makes its request, Pyth can compute the result, about 4 seconds before everyone else. Pyth can't change the result, but it could withhold the second half and leave the draw stuck. Pyth states this limitation in its own documentation.
3. Unlock and redrawunlockJackpot lets the owner unlock a draw that's waiting for its number, which is needed if Pyth never answers. But if the owner and Pyth cheat together, it's a way to throw away a bad result and draw again.
4. Pyth picks among a few resultsBecause the first half is just block data, a dishonest Pyth that controls when Megapot's request happens (by front-running Megapot's bot, or colluding with the sequencer) could compute a few results in advance and pick the one it likes. This is a theoretical scenario; I saw no sign of it in draw 133.
5. Pyth's secret seed leaksAnyone who gets the hash chain's starting number knows every result in advance. Safety depends on how well Pyth protects its own servers.

On audits: Trail of Bits audited Pyth Entropy (12/2023 to 01/2024) and reported 4 High-severity issues. Code4rena's audit of Megapot v2 (11/2025) includes M-05 (shared seed, fixed as shown above), M-06 and M-07 (changing the provider), M-01 (the owner changing parameters mid-draw) and H-02 (the reveal step running out of gas when the bonus maximum is too large). The public report doesn't say which issues were fixed; M-05 is the only one I could verify myself.

I haven't been able to read the source code of the live Megapot contracts, so the owner powers above come from the audited version. The file list of the live version adds Ownable2Step and AllowedManager, which means the access control has changed. I also haven't checked whether the owner is a single wallet or a multi-signature wallet.

How much does Megapot pay for randomness each draw?

Each request, Megapot pays Pyth Entropy a fee in ETH. For draw 133 it was 0.000045 ETH, about $0.11 to $0.18 with ETH between $2,500 and $4,000.

  • The fee has two parts: a fee for the provider and a fee for Pyth's shared fund. You can read the split with getProviderInfoV2 and getPythFee on Basescan.
  • The fee grows with the amount of gas the reveal step is allowed to use, because Pyth pays the gas for that transaction. Megapot asks for 4,000,000 gas, exactly the formula in the code: 1,500,000 plus 250,000 times the highest bonus (10). The bigger the pool, the higher the bonus maximum, so the fee goes up too.
  • The reveal transaction actually costs about 0.0000145 ETH in gas, paid by Pyth. The rest of the fee is Pyth's earnings.

The 5,000 USDC Guaranteed Prize in Megapot's post is a plain USDC transfer from wallet 0xF6a9…fd56. It's a promotion Megapot pays outside the contract and has nothing to do with the draw mechanism.

Conclusion

On transparency, Megapot's mechanism does well: every step is on-chain, anyone can check it, and draw 133 matched down to the last ball. On safety, players, outsiders and even the sequencer can't change the result. What's left is trust in two parties: Pyth, and Megapot's owner.

Two changes would cut that trust down a lot:

  • Megapot keeps its own secret number as the first half (hash it first, reveal it later), instead of letting Entropy build it from block data. Then Pyth would no longer know the result in advance.
  • Put the functions that change the random number source behind a mandatory waiting period (a timelock) and a multi-signature wallet, with events, so players can see a change coming before it takes effect.

Check any draw yourself

  1. On Basescan, open Megapot's ScaledEntropyProvider contract 0x5D03…Ae51, Events tab. Each draw has one EntropyFulfilled event just after 17:00 UTC; click it to open the reveal transaction.
  2. In the RevealedWithCallback event, copy the two halves, the commitment, numHashes and the random number into the checker above. The six balls must match the WinnersCalculated event.
  3. Look up the request's sequence number (and that number minus 1) on the Pyth Entropy Explorer to find the request transaction and the previous link.
  4. Check whether Jackpot 0x3bAe…42a2 has any warning events around that draw: EntropyUpdated (random source replaced), JackpotUnlocked (a draw in progress unlocked), EmergencyModeEnabled. A normal draw has none of these.
